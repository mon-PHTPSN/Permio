Permio Deterministic Milestones

A bilingual execution contract that fixes milestone order, artifacts, privacy invariants, tests, evidence, and binary completion gates for the Permio build.

Status: revised execution contract
Date: 10 October 2026
Scope: programmable scenario library, context-bound accounts, generated scenario packs, Midnight authorization, and composable execution

1 How completion is judged

“Deterministic” means every milestone has named artifacts, executable checks, privacy invariants, negative cases, and a binary exit gate. It does not mean that participant names or scenario data are fixed in architecture.

All concrete examples are generated by:

templateHash + generatorVersion + explicitSeed + policyProfile
  -> synthetic scenario instance and expected test vectors

The seed is recorded for reproducibility. Generated values are disposable and must never become protocol constants, source-code branches, contract literals, or hand-written architecture requirements.

1.1 Architecture status versus implementation status

The programmable scenario library, context accounts, scoped capabilities, three required scenario profiles, and separation of privacy authorization from execution are binding Permio design decisions, not optional future ideas. A milestone marked NOT_STARTED means the current checkout has not yet implemented that part of the authoritative design; it does not authorize an alternative fixed-domain architecture. Existing code is either conforming, partially conforming, or pending migration.

2 Global gates

Every milestone must preserve these rules:

  1. No global public pseudonym links a principal across scenario instances or contexts.
  2. An authorization binds template version, instance, context, action, resource, purpose, recipient, time, and disclosure policy.
  3. Delegation attenuates authority and has a bounded depth.
  4. Agents never receive blanket access or template self-approval power.
  5. Private records and witnesses never enter the gateway, execution chain, public application store, logs, or generated documentation.
  6. Privacy decisions and high-throughput execution use a versioned receipt boundary.
  7. Cross-context bridges are explicit, recipient-bound, purpose-bound, selected-record-bound, expiring, and tested against replay.
  8. A proof establishes only encoded claims, never the truth of an opinion, allegation, diagnosis, prediction, or human judgment.
  9. Tests use generated synthetic instances; production inputs never reuse test seeds.

4 M1 — Existing receipt-protocol baseline

Status: DONE; historical evidence remains in docs/evidence/M1

The repository already contains a canonical receipt schema package, EIP-712 encoding, hash vectors, a recipient-bound Solidity registry, and integration tests. Its named hand-written scenario fixture is retained only as historical evidence for that completed baseline. New architecture and tests must migrate to the generator introduced in M3; the legacy fixture is not a template, protocol requirement, or source for new acceptance criteria.

M1 remains complete only as a record of the implemented receipt slice. It does not claim that scenario templates, context accounts, or generic Midnight authorization are implemented.

5 M2 — Scenario-template domain package

Status: DONE; depends on M0; acceptance evidence is recorded in docs/evidence/M2/acceptance.json

Artifacts

  • ScenarioTemplate, ContextDefinition, ActionDefinition, and transition schemas;
  • canonical serialization and versioned template hash;
  • template namespace and semantic-version rules;
  • validator error taxonomy; and
  • unit and property tests.

Acceptance

  1. Unknown fields, missing fields, invalid references, unreachable states, and duplicate identifiers fail validation.
  2. Canonicalization is stable across object-key order and supported runtimes.
  3. An incompatible schema change requires a new template or protocol version.
  4. The domain package imports no application-specific scenario module.

Exit gate

M2 fails if supported contexts or actions are a closed TypeScript union tied to one use case, or if validation executes arbitrary template code.

Implemented result

packages/scenario-domain now owns the open template model, exact schema validation, graph and cross-reference checks, canonical Unicode-normalized serialization, length-delimited domain-separated SHA-256 hashing, and template revision compatibility. Its tests permute object-key order, exercise invalid graphs and references, prove that accessor code is not executed, and enforce a local-only production import boundary. Scenario catalog entries remain data to be governed in M4 and instantiated by the M3 generator; none is embedded as a closed application type.

6 M3 — Deterministic scenario generator

Status: NOT_STARTED; depends on M2

Artifacts

  • versioned generator interface;
  • seeded synthetic principal, record, credential, event, and timestamp generation;
  • public/private classification manifest;
  • golden-vector format; and
  • artifact privacy scanner.

Acceptance

  1. The same template hash, generator version, seed, and policy profile produce byte-identical canonical vectors.
  2. A different seed changes instance values without changing schemas or source code.
  3. Generated fixtures contain synthetic data only.
  4. The scanner fails when a field classified private appears in a public receipt, ledger dump, log, or generated HTML.

Exit gate

M3 fails if new tests import a hand-written named scenario fixture or compare against instance literals stored in architecture documents.

7 M4 — Template governance and library

Status: NOT_STARTED; depends on M2

Artifacts

  • draft, validation, review, activation, retirement, and revocation states;
  • reviewer attestations over exact template hashes;
  • namespace governance and threshold-approval model;
  • immutable active-version registry; and
  • authorization tests for authors, reviewers, governance, and allocators.

Acceptance

  1. Authors and Agents may draft but cannot self-activate a high-impact shared template.
  2. Validation tools report risk but cannot grant trust.
  3. Activation requires the configured threshold for the namespace.
  4. Retiring a template prevents new instances without rewriting historical receipts.
  5. An allocator can instantiate only an active version.

Exit gate

M4 fails if one administrator role implicitly owns authoring, approval, allocation, upgrades, and emergency revocation.

8 M5 — Context accounts and scoped sessions

Status: NOT_STARTED; depends on M2 and M4

Artifacts

  • ScenarioInstance, ContextAccount, CapabilityGrant, and ActionIntent;
  • capability attenuation, expiry, revocation, and delegation-depth logic;
  • session-key issuance and verification;
  • human, service, contract, and Agent principal types; and
  • denial-reason tests.

Acceptance

  1. Registration grants no permanent business role.
  2. Every action checks template, instance, context, action, resource, purpose, recipient, time, disclosure policy, and revocation state.
  3. A child grant cannot exceed any dimension of its parent.
  4. A session key can exercise only its declared subset before expiry.
  5. Changing one constrained dimension causes a precise denial.
  6. An Agent cannot activate templates or create unbounded delegations unless a distinct governance capability explicitly permits it.

Exit gate

M5 fails if login state alone authorizes a domain action or if the database stores a global role as the source of runtime permission.

9 M6 — Generic Midnight authorization boundary

Status: NOT_STARTED; depends on M2, M3, and M5

Artifacts

  • approved template and policy hash registry;
  • generic capability and ActionIntent verification adapters;
  • action-specific proof modules selected through versioned schema identifiers;
  • scoped-nullifier derivation; and
  • public DecisionReceipt fields.

Acceptance

  1. Private evidence and witness values remain inside the caller-controlled proof boundary.
  2. Public output contains only the receipt version, template/version reference, instance commitment, context, action schema, purpose, recipient, validity window, scoped nullifier, output commitment, and source reference.
  3. Nullifier domains separate templates, contexts, actions, resources, and policy versions.
  4. Replacing recipient, purpose, action, template version, or instance causes verification failure or a distinct non-reusable receipt.
  5. Unsupported schema identifiers fail closed.

Exit gate

M6 fails if the Compact contract or adapter branches on generated participant names, generated identifiers, or one template family's literal values.

10 M7 — Gateway and durable receipt transport

Status: NOT_STARTED; depends on M6

Artifacts

  • finalized Midnight event observer;
  • source-network, contract, transaction, and policy verification;
  • versioned typed receipt envelope;
  • durable outbox with idempotent retries; and
  • gateway key-rotation tests.

Acceptance

  1. The gateway receives no private credential, record, witness, session key, or plaintext evidence.
  2. It signs only allowlisted receipt and template versions from configured Midnight sources.
  3. Restarting at every durable boundary produces at most one logical execution record.
  4. A stale, reorged, malformed, unknown, or expired source is rejected.
  5. Gateway authority is separate from governance, issuer, allocator, Agent, and relayer authority.

Exit gate

M7 fails if the gateway re-evaluates private policy, silently widens a receipt, or relies on in-memory retry state.

11 M8 — Execution registry and adapters

Status: IN_PROGRESS; the existing recipient-bound registry is a partial implementation and must be generalized after M6 and M7.

Artifacts

  • versioned DecisionReceipt verification;
  • signer rotation and threshold-ready governance boundary;
  • recipient, purpose, expiry, schema, and replay checks;
  • adapter interface for Monad contracts and ordinary applications; and
  • negative tests for widening and replay.

Acceptance

  1. The executor performs only the action named by the receipt schema.
  2. Wrong recipient, purpose, version, signer, source, expiry, or replay scope is rejected.
  3. The relayer pays execution cost but cannot create or modify authorization.
  4. Execution may fail because local state changed, but failure does not mutate the underlying privacy authorization.
  5. No stable subject identifier is required by the registry.

Exit gate

M8 fails if an execution adapter can reinterpret one receipt as a broader action or if the registry owner also acts as the receipt signer by default.

12 M9 — Cross-domain generated scenario packs

Status: NOT_STARTED; depends on M3 through M8

Required packs

  1. Clinical referral and research consent.
  2. Professional qualification and temporary site access.
  3. Delegated financial or purchasing Agent.

Each pack contains a template, policy profile, generator rules, generated positive and negative instances, disclosure previews, expected receipts, and privacy scans. It contains no hand-authored participant or record fixture.

Acceptance

  1. The healthcare pack separates treatment, research, and optional emergency purposes, recipients, periods, and audit duties.
  2. The professional pack proves a current qualification without disclosing a full transcript or unrelated history and creates only short-lived access.
  3. The Agent pack binds counterparty, action, bounded resource or amount policy, expiry, delegation depth, and revocation.
  4. All packs run through the same scenario, capability, receipt, gateway, and execution interfaces.
  5. No pack requires adding a participant name, context literal, or branching rule to the core domain.

Exit gate

M9 fails if “supporting” a new pack means copying the core system and renaming fields, or if any pack bypasses the common privacy invariants.

13 M10 — Encrypted evidence and cross-context bridge

Status: NOT_STARTED; depends on M6 and M9

Artifacts

  • selected-record manifest;
  • recipient encryption and key-rotation interface;
  • explicit cross-context ActionIntent;
  • bridge receipt and revocation/expiry behavior; and
  • evidence-vault verification API.

Acceptance

  1. The user sees source context, destination context, recipient, purpose, selected records, expiry, and newly created link before authorization.
  2. Ciphertext travels separately from the public receipt.
  3. The recipient verifies manifest hashes, source commitments, receipt scope, and expiry before decryption.
  4. Unrelated records and other instances cannot be enumerated.
  5. Changing recipient, purpose, record set, destination context, or case scope invalidates the bridge.

Exit gate

M10 fails if a bridge is implicit, globally reusable, plaintext on a public ledger, or described as proving the truth of the underlying human claim.

14 M11 — Scenario-library product workflow

Status: NOT_STARTED; depends on M4, M5, and M9

Artifacts

  • template catalogue and version view;
  • draft, review, activation, retirement, and instantiation workflows;
  • slot-assignment and capability-delegation UI;
  • disclosure and execution preview;
  • Agent-session management and revocation; and
  • isolated multi-account browser journeys generated from scenario packs.

Acceptance

  1. The UI never presents account registration as permanent role selection.
  2. Users can distinguish template, instance, context, account, capability, session, proof, receipt, execution, and evidence delivery.
  3. Every sensitive action shows recipient, purpose, expiry, disclosed claims, and new linkage before confirmation.
  4. Reviewers see the exact template hash and version being approved.
  5. Agents show their active scope and provide immediate revocation.
  6. Browser journeys are created from generated packs rather than fixed user names or a scenario-runner embedded in production UI.

Exit gate

M11 fails if product navigation assumes one domain, if a perspective selector impersonates other users, or if administrator credentials appear in the UI.

15 M12 — Local and public-network evidence

Status: NOT_STARTED; depends on M7 through M11

Artifacts

  • local Midnight and local EVM end-to-end evidence;
  • configured public test-network deployment evidence;
  • restart, reorg, expiry, revocation, and replay drills;

Acceptance

Permio 确定性里程碑

一份完整的双语执行契约，固定 Permio 构建的里程碑顺序、产物、隐私不变量、测试、证据与二元完成门槛。

状态：修订后的执行契约
日期：2026 年 10 月 10 日
范围：可编程情境库、上下文账户、生成式情境包、Midnight 授权与可组合执行

1 如何判断完成

“确定性”表示每个里程碑都有具名产物、可执行检查、隐私不变量、负向案例和二元退出门槛。 它不表示参与者姓名或情境数据要写死在架构中。

所有具体示例都由下式生成：

模板哈希 + 生成器版本 + 显式种子 + 策略 profile
  -> 合成情境实例与预期测试向量

种子被记录以便复现。生成值是可丢弃数据，绝不能变成协议常量、源码分支、合约字面量或手写 架构要求。

1.1 架构状态与实施状态

可编程情境库、上下文账户、有限能力、三个必需情境 profile，以及隐私授权与执行分离，都是 具有约束力的 Permio 设计决策，而不是可选的未来设想。里程碑标记为 NOT_STARTED，只表示当前 checkout 尚未实现权威设计的这一部分；它不允许继续采用另一套固定领域架构。现有代码只能是 已经符合、部分符合或等待迁移。

2 全局门槛

每个里程碑都必须保持以下规则：

  1. 不存在把主体跨情境实例或上下文关联起来的全局公开假名。
  2. 授权绑定模板版本、实例、上下文、操作、资源、用途、接收方、时间和披露策略。
  3. 委托只能收缩权限，并且深度有界。
  4. Agent 永远不会获得全面访问或自行批准模板的权力。
  5. 私有记录和见证绝不进入网关、执行链、公开应用存储、日志或生成文档。
  6. 隐私决定与高吞吐执行使用版本化收据边界。
  7. 跨上下文桥接必须显式、接收方绑定、用途绑定、选定记录绑定、会到期并经过重放测试。
  8. 证明只建立已编码声明，绝不证明观点、指控、诊断、预测或人的判断为真。
  9. 测试使用生成的合成实例；生产输入绝不复用测试种子。

5 M2——情境模板领域包

状态：DONE；依赖 M0；验收证据记录于 docs/evidence/M2/acceptance.json

产物包括 ScenarioTemplate、ContextDefinition、ActionDefinition、转换模式、规范序列化、 版本化模板哈希、命名空间与语义版本规则、验证错误分类，以及单元和属性测试。

验收必须证明：未知、缺失或重复字段以及无效引用和不可达状态会失败；规范化不受对象键顺序 影响；不兼容变更需要新版本；领域包不导入特定应用情境模块。

已实现结果

8 M5——上下文账户与有限会话

状态：NOT_STARTED；依赖 M2 和 M4

9 M6——通用 Midnight 授权边界

状态：NOT_STARTED；依赖 M2、M3 和 M5

验收必须证明：私有证据留在调用者控制的证明边界；公开输出只有最小版本化收据；空值标识域 分离模板、上下文、操作、资源和策略版本；替换任何绑定维度都会失败或产生不可复用的新收据； 不支持的模式默认拒绝。

如果 Compact 合约或适配器根据生成的姓名、标识符或某一模板族的字面值分支，M6 失败。

10 M7——网关与持久化收据传输

状态：NOT_STARTED；依赖 M6

验收必须证明：网关不接收私有数据；只为允许的来源和版本签名；在每个持久化边界重启仍最多 产生一个逻辑执行记录；陈旧、重组、畸形、未知或过期来源被拒绝；网关权限与其他权限分离。

如果网关重新评估私有策略、扩大收据或依赖内存重试状态，M7 失败。
