Permio Deterministic Milestones

A bilingual execution contract that fixes milestone order, artifacts, privacy invariants, tests, evidence, and binary completion gates for the Permio build.

Status: implementation contract
Date: 9 October 2026
Scope: Alice, Bob, and Clara composite flow across Midnight and Monad

1 Purpose and completion rule

This document converts the composite architecture into a sequential execution contract. A milestone is complete only when every named artifact exists, every acceptance test passes, every privacy invariant is demonstrated, and its acceptance record is committed. Partial behavior, screenshots without machine evidence, and an implementation that merely resembles the target do not count.

"Deterministic" means the observable result is fixed: schemas, public fields, private fields, state transitions, file locations, failure behavior, and test evidence are prescribed. Internal code organization inside a named module may vary only when it does not change those outputs.

Milestones are strictly ordered. Work may be researched in advance, but code for milestone M(n+1) must not be merged into main before M(n) has a passing acceptance record. A milestone has exactly four states:

  • NOT_STARTED: no implementation has been accepted.
  • IN_PROGRESS: implementation exists but at least one exit condition fails.
  • BLOCKED: an external dependency prevents a required exit condition.
  • COMPLETE: all exit conditions pass at one recorded commit.

The acceptance record for milestone MN is docs/evidence/MN/acceptance.json. It contains the milestone ID, Git commit, tool versions, commands, test result summaries, deployment identifiers when applicable, and SHA-256 hashes of non-Git evidence. It contains no private witness, mnemonic, credential, signing key, cookie, or personal data.

Required outbox lifecycle

MIDNIGHT_CONFIRMED
-> ATTESTATION_PREPARED
-> ATTESTATION_SIGNED
-> MONAD_SUBMITTED
-> MONAD_FINALIZED
-> CONSUMED | REVOKED

The idempotency key binds Midnight network, Compact contract, Midnight transaction, schema, purpose, recipient, Monad chain ID, and registry address.

Binary acceptance gate

  1. The observer rejects the wrong network, contract, circuit/action, or public commitment.
  2. The policy rejects unapproved schema-purpose-recipient combinations.
  3. The gateway signs with the verifier key; the relayer submits with a different key.
  4. A relay nullifier changes if recipient, purpose, chain ID, or registry address changes.
  5. Two workers processing one outbox row produce at most one accepted Monad receipt.
  6. Restarting at every lifecycle state converges on one final attestation ID.
  7. The outbox and logs contain no Midnight witness data.
  8. Expired and revoked receipts are not reported as valid.

Rejection conditions

M4 fails if the gateway accepts a client assertion without reading Midnight, if verifier and relayer keys are equal, or if an in-memory queue is the only record of a submitted transaction.

15 Cross-milestone rules

Change control

After M1, changing a schema, purpose, encoding, domain separator, EIP-712 field, public Compact output, or acceptance fixture requires a protocol decision record under docs/decisions/, a version increment, migration impact, updated vectors, and updated tests. Editing an expected value solely to make a failing test pass is prohibited.

Evidence quality

Every acceptance command must be reproducible from the referenced commit. Screenshots may supplement but never replace assertions, receipts, or manifest checks. Live-network identifiers are public evidence; secrets are never evidence. Machine-generated evidence must be redacted before commit.

Definition of blocked

A milestone may be BLOCKED only when a required external service or network is unavailable, a required platform defect has been reproduced, or an owner decision is genuinely missing. A failing test, unfinished implementation, or uncertain design is IN_PROGRESS, not BLOCKED.

Definition of done

The result of a milestone is the exact committed artifacts plus passing gates, not a progress percentage. If one required negative test, privacy scan, restart test, manifest, or acceptance record is missing, the milestone remains IN_PROGRESS.

1 目标与完成规则

本文档把复合架构转化为严格顺序执行的实施契约。只有当指定产物全部存在、验收测试全部 通过、隐私不变量得到证明，并且验收记录已提交时，一个里程碑才算完成。部分功能、缺少 机器证据的截图，或者只是与目标相似的实现，都不能算完成。

“确定性”表示可观察结果是固定的：模式、公开字段、私有字段、状态转换、文件位置、失败 行为和测试证据均已规定。命名模块内部的代码组织可以不同，但不能改变这些结果。

里程碑必须严格按顺序完成。可以提前研究后续工作，但 M(n) 没有通过验收时， M(n+1) 的代码不能合并到 main。状态只有 NOT_STARTED、IN_PROGRESS、BLOCKED 和 COMPLETE 四种。每个 MN 的验收记录固定为 docs/evidence/MN/acceptance.json，记录提交、工具版本、命令、测试摘要、必要的公开部署 标识和非 Git 证据的 SHA-256 哈希，但绝不包含 witness、助记词、凭证、私钥、Cookie 或 个人数据。

2 固定协议决策

Monad 的模式 ID 和用途哈希是上述精确 UTF-8 字符串的 keccak256。Monad 中继空值标识 绑定 Midnight 限定范围空值标识、模式、用途、接收方、Monad 链 ID 和注册表地址；原始 Midnight 空值标识不得直接复制到 Monad 交易。
