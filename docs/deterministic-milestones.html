Permio Deterministic Milestones

A bilingual execution contract that fixes milestone order, artifacts, privacy invariants, tests, evidence, and binary completion gates for the Permio build.

Status: implementation record through M5; deterministic execution contract for M6–M12
Date: 11 October 2026
Scope: programmable scenario library, context-bound accounts, generated scenario packs, Midnight authorization, and composable execution

1 How completion is judged

“Deterministic” means every milestone has named artifacts, executable checks, privacy invariants, negative cases, and a binary exit gate. It does not mean that participant names or scenario data are fixed in architecture.

All concrete examples are generated by:

templateHash + generatorVersion + explicitSeed + policyProfile
  -> synthetic scenario instance and expected test vectors

The seed is recorded for reproducibility. Generated values are disposable and must never become protocol constants, source-code branches, contract literals, or hand-written architecture requirements.

1.1 Architecture status versus implementation status

The programmable scenario library, context accounts, scoped capabilities, three required scenario profiles, and separation of privacy authorization from execution are binding Permio design decisions, not optional future ideas. A milestone marked NOT_STARTED means the current checkout has not yet implemented that part of the authoritative design; it does not authorize an alternative fixed-domain architecture. Existing code is either conforming, partially conforming, or pending migration.

2 Global gates

Every milestone must preserve these rules:

  1. No global public pseudonym links a principal across scenario instances or contexts.
  2. An authorization binds template version, instance, context, action, resource, purpose, recipient, time, and disclosure policy.
  3. Delegation attenuates authority and has a bounded depth.
  4. Agents never receive blanket access or template self-approval power.
  5. Private records and witnesses never enter the gateway, execution chain, public application store, logs, or generated documentation.
  6. Privacy decisions and high-throughput execution use a versioned receipt boundary.
  7. Cross-context bridges are explicit, recipient-bound, purpose-bound, selected-record-bound, expiring, and tested against replay.
  8. A proof establishes only encoded claims, never the truth of an opinion, allegation, diagnosis, prediction, or human judgment.
  9. Tests use generated synthetic instances; production inputs never reuse test seeds.

3 M0 — Documentation and naming baseline

Result in plain language

M0 established what Permio is, which system boundaries exist, and how later work is documented and verified. A developer can begin from the repository without guessing whether private authorization happens on Midnight, whether the gateway may receive private evidence, or whether Monad is the privacy system. The answer is fixed: Midnight is the private authorization boundary, the gateway transports a minimal finalized result, and Monad consumes a recipient-bound public attestation.

M0 also established that concrete people, records, purchases, cases, amounts, and timestamps are examples or generated test data—not protocol constants. “Alice”, “Bob”, and “Clara” may explain a historical flow, but core code and new acceptance tests cannot depend on those names.

  • docs/PERMIO_FROM_NEED_TO_DESIGN.md, the human-first explanation of the product need and privacy model;

Actors and responsibilities fixed by M0

  • A template author describes a reusable scenario but does not thereby gain approval or runtime authority.
  • A user or Agent acts only through a context-specific authorization; account registration alone grants no business permission.
  • Midnight verifies private authorization and publishes only the minimum versioned result required downstream.
  • The gateway observes finalized public Midnight output. It must not receive the user's private credential, record, witness, or plaintext evidence.

4 M1 — Existing receipt-protocol baseline

Status: DONE
Implementation commit: d5982c9d1994adc63ad6e2c644670cecc59914d5
Acceptance evidence: docs/evidence/M1/acceptance.json

Result in plain language

M1 implemented the first executable public-receipt slice. It answers a narrow question: after some upstream privacy system has produced an authorization, how can a verifier sign an exact recipient-bound statement and how can a Monad-compatible contract reject altered, expired, unauthorized, or replayed statements?

It does not answer whether the upstream private action was actually valid. The existing Solidity contract verifies the gateway/verifier signature and the public receipt constraints; it does not verify a Midnight proof.

Concrete protocol data

@permio/protocol defines versioned schema and purpose identifiers, canonical length-delimited commitment inputs, and the EIP-712 typed-data layout. EIP-712 is the Ethereum standard that signs named structured fields rather than an ambiguous byte string.

The public attestation binds:

  • schema ID;
  • Midnight source network, contract, and transaction hashes;
  • action commitment and scoped nullifier;
  • purpose hash and exact Monad recipient;
  • issue and expiry times; and
  • the EIP-712 chain and verifying-contract domain.

The scoped nullifier is a one-use identifier limited to a particular schema, purpose, and recipient. It prevents the same entitlement from being consumed twice without publishing a reusable identity for the user.

Implemented transaction flow

  1. An authorized verifier signs the exact EIP-712 attestation.
  2. A relayer submits the attestation and signature to RecipientBoundAttestationRegistry.registerAttestation.
  3. The contract checks time validity, exact recipient binding, verifier authorization, signature recovery, and unused replay scope.
  4. On success, the contract records the attestation and consumes the scope.
  5. On failure, no attestation or replay state is written.

Tests and negative cases

  • protocol tests prove schema and purpose hashes match committed vectors;
  • canonical encoding distinguishes inputs that naive concatenation would make ambiguous;
  • commitment domains are pairwise separated so one hash type cannot be reused as another;
  • Solidity and TypeScript agree on the EIP-712 field order and type hash;
  • a valid relayed registration succeeds on Hardhat's local EVM;
  • recipient substitution, replay, and an unauthorized verifier fail; and
  • revoking a verifier prevents later signatures from being accepted.

Verified evidence and limitation

The accepted run used Node.js 24.13.1, npm 11.8.0, TypeScript 7.0.2, Hardhat 3.14.0, and viem 2.55.19. npm run check passed six protocol tests and six deployed-contract tests.

The hand-written Alice/Bob/Clara fixture remains only as historical M1 test evidence. New scenario work must use M3 generation. M1 does not implement scenario templates, governance, context accounts, a gateway, or Midnight proof verification.

Exit gate

M1 is not complete if TypeScript and Solidity hash different payloads, if an attestation can be replayed or redirected to another recipient, or if a relayer can create authorization without an authorized verifier signature.

5 M2 — Scenario-template domain package

Status: DONE; depends on M0; acceptance evidence is recorded in docs/evidence/M2/acceptance.json
Implementation commit: 51197e36fffa04d29162ea9b7ff300e6e1b2c10a

Artifacts

  • ScenarioTemplate, ContextDefinition, ActionDefinition, and transition schemas;
  • canonical serialization and versioned template hash;
  • template namespace and semantic-version rules;
  • validator error taxonomy; and
  • unit and property tests.

Result in plain language

M2 created the language used to describe a reusable scenario. A template says which contexts exist, which participant slots may be filled, which record and claim shapes are recognized, which actions are available, which disclosures each action permits, and how an action moves an instance from one state to the next. These definitions are data validated by a fixed parser; they are not JavaScript callbacks or application-specific code.

For example, the core understands that an action references a context, resource rule, disclosure policy, and state transition. It does not contain a hard-coded union such as “review”, “support”, or “clinical referral”. Those identifiers belong to governed template data.

Exact processing flow

  1. parseScenarioTemplate rejects values that are not exact JSON data.
  2. It rejects missing and unknown fields instead of silently defaulting them.
  3. It checks identifier uniqueness and resolves every cross-reference.
  4. It checks that all declared states are reachable and that one state/action pair cannot select two different transitions.
  5. Canonicalization normalizes strings to Unicode NFC, sorts object keys, and preserves meaningful array order.
  6. hashScenarioTemplate applies a versioned, length-delimited, domain-separated SHA-256 hash to the canonical template.
  7. Revision checks require semantic-version changes appropriate to the actual compatibility impact.

Acceptance

  1. Unknown fields, missing fields, invalid references, unreachable states, and duplicate identifiers fail validation.
  2. Canonicalization is stable across object-key order and supported runtimes.
  3. An incompatible schema change requires a new template or protocol version.
  4. The domain package imports no application-specific scenario module.
  5. Patch versions may change prose only; additive compatible changes require a minor version; breaking semantic changes require a major version.
  6. Template getters, proxies, or accessors cannot execute during validation.
  7. Production package imports remain local or Node built-ins, preserving the application-neutral boundary.

Exit gate

M2 fails if supported contexts or actions are a closed TypeScript union tied to one use case, or if validation executes arbitrary template code.

Implemented result

packages/scenario-domain now owns the open template model, exact schema validation, graph and cross-reference checks, canonical Unicode-normalized serialization, length-delimited domain-separated SHA-256 hashing, and template revision compatibility. Its tests permute object-key order, exercise invalid graphs and references, prove that accessor code is not executed, and enforce a local-only production import boundary. Scenario catalog entries remain data to be governed in M4 and instantiated by the M3 generator; none is embedded as a closed application type.

Tests and verified evidence

Fifteen M2 tests cover unknown and missing fields, duplicate identifiers, invalid references, unreachable and ambiguous graphs, 64 object-key-order permutations, Unicode normalization, length and domain separation, revision compatibility, open identifiers, accessor non-execution, and package import boundaries. The accepted full repository check passed those tests together with the earlier protocol and Solidity suites.

M2 deliberately does not decide whether a valid template is trustworthy or active. Structural validity is input to M4 governance, not permission to use a template.

6 M3 — Deterministic scenario generator

Status: DONE; depends on M2
Implementation commit: 38227d45c7a2f409ebeb0a0d1be0bec877cdaecc
Acceptance evidence: docs/evidence/M3/acceptance.json

Result in plain language

M3 replaced hand-written example identities and records with reproducible, synthetic test instances. Given the same validated template, exact template hash, generator version, test: seed, and policy profile, the generator emits the same canonical bytes on every run. Changing the seed changes generated principals and records without changing source code or the scenario schema.

This generator is for tests, demonstrations, and acceptance evidence. It is not a production identity generator and never reads production data.

Artifacts

  • versioned generator interface;
  • seeded synthetic principal, record, credential, event, and timestamp generation;
  • public/private classification manifest;
  • golden-vector format; and
  • artifact privacy scanner.

The concrete package is packages/scenario-generator. Its version-1 golden vector stores the complete deterministic input, canonical output bytes in lowercase hexadecimal, and a domain-separated digest. The vector is a private test artifact because it contains generated private fields; it is not a public receipt.

Generation flow

  1. Validate the supplied M2 template and recompute its exact hash.
  2. Reject a mismatch between the template and caller-supplied hash.
  3. Validate the generator version, explicit test: seed, and policy profile.
  4. Derive a master SHA-256 digest from length-prefixed inputs.
  5. Derive each principal, record, credential, claim, event, and timestamp under its own versioned hash domain.
  6. Derive distinct principals for each (context, participant slot) pair so a reused slot does not create a global cross-context identifier.
  7. Produce private instance data separately from the allowlisted public schema summary.
  8. Rebuild the exhaustive classification manifest and scan every purported public artifact before accepting it.

The generator never reads the system clock, operating-system randomness, locale, environment variables, or machine-specific state. Synthetic values are prefixed with syn_ so fixtures can reject accidental production data.

Acceptance

  1. The same template hash, generator version, seed, and policy profile produce byte-identical canonical vectors.
  2. A different seed changes instance values without changing schemas or source code.
  3. Generated fixtures contain synthetic data only.
  4. The scanner fails when a field classified private appears in a public receipt, ledger dump, log, or generated HTML.
  5. The scanner detects raw, JSON-escaped, HTML-escaped, numeric-entity, URL-encoded, hexadecimal, Base64, and Base64URL forms of classified private strings.
  6. Removing or weakening a private classification fails because the manifest is re-derived from the generated shape rather than trusted from the caller.
  7. The committed golden vector is regenerated byte-for-byte by npm run generate:golden --workspace @permio/scenario-generator.

Tests and verified evidence

Fourteen generator tests cover complete-input validation, hash mismatch, determinism, seed separation, context-specific principals, synthetic values, explicit timestamps, byte-stable canonical output, golden-vector reproduction, exhaustive classification, and privacy-leak encodings. npm run check passed M0–M3 tests and the six deployed Solidity tests.

The privacy scanner is an acceptance guard, not a claim that it can reverse encryption, compression, hashing, chunking, or unlimited nested encodings.

Exit gate

M3 fails if new tests import a hand-written named scenario fixture or compare against instance literals stored in architecture documents.

7 M4 — Template governance and library

Status: DONE; depends on M2 and is integrated above M3
Implementation commit: 9b76d6117cabf7211b5077c12357bdc6a3cd251e
Acceptance evidence: docs/evidence/M4/acceptance.json
Development log: docs/evidence/M4/development-log.md

Result in plain language

M4 determines when one exact M2 template version may be used to create new scenario instances. It separates creating a draft, reporting validation risk, reviewing the exact content, activating it, allocating instances, retiring it, and revoking it in an emergency. No universal administrator can perform all of those actions.

A template is identified by four inseparable values: namespace, template ID, semantic version, and exact SHA-256 content hash. Approval of one combination never approves another version or altered content.

Artifacts

  • draft, validation, review, activation, retirement, and revocation states;
  • reviewer attestations over exact template hashes;
  • namespace governance and threshold-approval model;
  • immutable active-version registry; and
  • authorization tests for authors, reviewers, governance, and allocators.

The package packages/scenario-governance implements the lifecycle registry, authority policy, stable error codes, Ed25519 reviewer attestations, immutable history records, and sixteen governance tests.

Authority model

Each namespace policy contains five non-overlapping sets:

  • authors create drafts and advance only their own draft through validation;
  • reviewers approve or reject an exact target with registered public keys;
  • governance authorities activate a sufficiently reviewed version and retire an active version;
  • allocators request permission to create one instance from an active exact version; and
  • emergency revokers prospectively stop an active or retired version.

Policy creation rejects an actor present in more than one set, duplicate reviewer identities, duplicate reviewer keys, empty required authority sets, and thresholds that cannot be reached. Being an Agent or an author never implicitly grants review, activation, allocation, or revocation authority.

Lifecycle and exact transitions

draft -> validated -> in_review -> active -> retired
                                    |          |
                                    +-> revoked<+
  1. createDraft reparses the M2 template, computes its exact hash, and reserves its namespace/template/version lineage.
  2. recordValidation stores structural and risk findings with grantsTrust: false; it cannot approve or activate anything.
  3. submitForReview freezes the exact target for reviewer decisions.
  4. submitReview verifies reviewer eligibility and the signature over the namespace, template ID, version, content hash, reviewer, decision, and time.
  5. activate requires a separate governance actor, enough unique approvals, no recorded rejection, and no duplicated reviewer decision.
  6. authorizeInstantiation requires an allocator, a unique request ID, the exact active target, and the current active state.
  7. retire prevents future allocations while preserving activation and prior allocation history.
  8. revoke records an explicit prospective emergency stop and reason without rewriting earlier records.

Acceptance

  1. Authors and Agents may draft but cannot self-activate a high-impact shared template.
  2. Validation tools report risk but cannot grant trust.
  3. Activation requires the configured threshold for the namespace.
  4. Retiring a template prevents new instances without rewriting historical receipts.
  5. An allocator can instantiate only an active version.
  6. Every review signature fails if any target field, reviewer identity, decision, time, key, domain, or signature is changed.
  7. A rejection blocks activation even when the numeric approval threshold is otherwise met.
  8. Termination cannot be backdated before an already-issued instantiation authorization.
  9. Returned records are cloned so a caller cannot mutate registry history.

Negative tests and verified evidence

The sixteen tests cover unauthorized authors, overlapping authority sets, Agent privilege escalation, same-version content replacement, invalid state transitions, validation attempting to grant trust, altered hashes and signed fields, ineligible and duplicate reviewers, insufficient thresholds, reviewer rejection, collapsed allocator/governance authority, allocation before activation, retirement, revocation, backdating, and attempted mutation of returned records.

The accepted npm run check passed six protocol, fifteen scenario-domain, fourteen generator, sixteen governance, and six deployed-contract tests. M4 remains an in-memory off-chain governance package; it does not claim that Midnight currently enforces this lifecycle.

Exit gate

M4 fails if one administrator role implicitly owns authoring, approval, allocation, upgrades, and emergency revocation.

8 M5 — Context accounts and scoped sessions

Status: DONE; depends on M2 and M4
Implementation commit: c65cfe1dfcc31019754ac807b00819ec55b0542b
Acceptance evidence: docs/evidence/M5/acceptance.json
Development log: docs/evidence/M5/development-log.md

Result in plain language

M5 turns one M4-approved allocation into a running scenario instance and decides whether a particular signed action may change that instance. It does not use a global role such as “administrator”, “merchant”, or “agent” as permission. Authority always comes from a capability bound to one exact template, instance, context, action scope, recipient scope, purpose, disclosure policy, and time window.

A context account is not a login account. It is a public key bound to one scenario instance and one template-defined context. Registration creates that binding but grants no action. An explicitly named instance issuer must create a root capability before the account can do anything.

Artifacts

  • ScenarioInstance, ContextAccount, CapabilityGrant, and ActionIntent;
  • capability attenuation, expiry, revocation, and delegation-depth logic;
  • session-key issuance and verification;
  • human, service, contract, and Agent principal types; and
  • denial-reason tests.

The concrete package is packages/context-accounts. It contains the runtime model, Ed25519 ActionIntent signing and verification, the authorization system, stable error types, and thirteen tests. Human, service, contract, and Agent principals all use the same capability checks.

Instance creation

  1. createScenarioInstance loads an unused M4 instantiation authorization.
  2. It reloads the governed template and requires that the template is still active at instance-creation time.
  3. It reparses the M2 template, recomputes its hash, and compares namespace, template ID, version, and hash with the M4 authorization.
  4. It records the allocator, initial template state, lifetime, and explicit capability issuers.
  5. It consumes the M4 allocation once. A stale allocation cannot be reused, and an allocation issued before retirement cannot create an instance after retirement.

Capability and session rules

A capability lists allowed actions, resource selectors and concrete resources, purposes, recipient kinds and exact recipients, disclosure policies, validity window, and remaining delegation depth. Delegation is valid only when the child is a strict subset of the parent: it must narrow at least one dimension, cannot add any value, cannot start earlier or end later, and cannot increase delegation depth. The implementation caps depth at 16 and treats revocation of any ancestor as revocation of its descendants.

A session receives a fresh Ed25519 public key and a strict subset of one capability. Account keys cannot be reused as session keys, and a key cannot be reused across context accounts. These rules prevent a convenient reusable key from becoming an accidental public cross-context identifier.

Signed action and authorization flow

The signed ActionIntent binds the exact template target, instance, session, context, action, resource selector, concrete resource, purpose, recipient kind, exact recipient, disclosure policy, issue time, and session-scoped nonce.

authorizeAction checks, in order:

  1. the session exists and its Ed25519 signature is valid;
  2. template, instance, and context match exactly;
  3. instance, account, capability ancestry, grant, and session are not revoked;
  4. the instance, grant, and session are within their validity windows;
  5. the (session ID, nonce) pair has not already been consumed;
  6. action, current state, resource, purpose, recipient, and disclosure policy are within the session and capability scopes; and
  7. the template defines exactly one permitted transition from the current state for that action.

Only after every check succeeds does the system consume the nonce and update the instance to the next state. A denial does not consume the nonce or mutate the instance.

Acceptance

  1. Registration grants no permanent business role.
  2. Every action checks template, instance, context, action, resource, purpose, recipient, time, disclosure policy, and revocation state.
  3. A child grant cannot exceed any dimension of its parent.
  4. A session key can exercise only its declared subset before expiry.
  5. Changing one constrained dimension causes a precise denial.
  6. An Agent cannot activate templates or create unbounded delegations unless a distinct governance capability explicitly permits it.
  7. Reusing an account or session key across contexts is rejected.
  8. Revoking an instance, context account, ancestor grant, grant, or session blocks every later affected action without deleting history.
  9. Changing one signed field either invalidates the signature or returns the precise denial for that constrained dimension.
  10. The authorization result records previous and next instance state and the exact account/grant/session chain used for the decision.

Denial results

Ordinary authorization failure returns one of nineteen stable reasons rather than relying on error-message prose:

UNKNOWN_SESSION, INVALID_SIGNATURE, TEMPLATE_MISMATCH, INSTANCE_MISMATCH,
INSTANCE_REVOKED, INSTANCE_EXPIRED, CONTEXT_MISMATCH, ACCOUNT_REVOKED,
GRANT_REVOKED, SESSION_REVOKED, NOT_YET_VALID, EXPIRED, ACTION_DENIED,
STATE_DENIED, RESOURCE_DENIED, PURPOSE_DENIED, RECIPIENT_DENIED,
DISCLOSURE_POLICY_DENIED, REPLAYED_INTENT

Negative tests and verified evidence

The thirteen tests cover missing or stale M4 allocation, template/hash mismatch, retirement before instance creation, all four principal kinds, cross-context key reuse, unauthorized root issuance, every scope-expansion attempt, unbounded and excessive delegation, over-broad or non-fresh sessions, ancestor revocation, exact state transition, mutation of every signed field, single-dimension denials, time windows, nonce replay, and all four runtime revocation boundaries.

The accepted full check passed generated-document freshness, TypeScript, Solidity 0.8.31 compilation for the Osaka EVM target, six protocol tests, fifteen domain tests, fourteen generator tests, sixteen governance tests, thirteen context-account tests, and six deployed-contract tests on Hardhat's local EVM.

Those contract tests prove the existing Monad registry did not regress; they do not claim M5 capability decisions are enforced on-chain. M5 is an in-memory off-chain component. It does not persist state, authenticate network callers, generate a Midnight proof, publish a DecisionReceipt, or execute a Monad action.

Exit gate

M5 fails if login state alone authorizes a domain action or if the database stores a global role as the source of runtime permission.

Result required in plain language

M6 moves the authorization decision that M5 currently evaluates in memory into a real, application-neutral Midnight boundary. It does not upload all M4/M5 state and does not place all state behind one opaque root. Shared governance facts are public records; large authority and credential-status collections use roots; individual permissions remain private signed assertions; private instance state uses commitments and sequences; one-use actions use nullifiers.

M4 remains responsible for validating Ed25519 reviewer attestations, unique eligible reviewers, namespace thresholds, rejection state, and separation of duties. M6 admits the resulting exact activation through a replay-protected envelope signed by the namespace governance-activator under the allowlisted midnight-jubjub-schnorr-v1 profile. M6 v1 does not register a second Midnight key for every reviewer and does not claim to re-run M4's threshold on-chain.

For an action that changes authorization state, Midnight becomes the authority that orders the transition. It verifies the old commitment and sequence, consumes the action nullifier, installs the next commitment, and increments the sequence atomically. Monad execution remains a later and separate result.

Exact state representation

  1. Each active, retired, or revoked template version is a directly readable ledger record. The full JSON, reviews, comments, and risk prose remain off-chain.
  2. Namespace authority leaves bind namespace, governance-policy version, authority kind, authority-key hash, and validity window.
  3. Runtime credential status uses a current-status keyed Merkle tree. Every credential commitment has exactly one current active or revoked leaf. The contract stores the latest root and monotonically increasing sequence.
  4. A proof must show membership of the exact active leaf in the current root; revocation replaces it with revoked. M6 does not rely on unspecified Merkle non-membership behavior.
  5. The baseline introduces no separate instance-authority root. Allocator and capability-issuer assertions are private, checked against the namespace authority root, and committed into private instance state.
  6. Root updates are verified transitions, not operator-supplied snapshots. An authority-root update binds old root, new root, policy version, effective sequence, and governance authorization. A credential-status update proves the old leaf/path, verifies its issuer or revoker, calculates the new leaf, and advances the root and sequence atomically.

Proof-module governance

Templates may select and configure only a registered exact active module. They cannot contain executable expressions, choose latest, substitute an implementation hash, or independently deploy proof code. A missing proof family returns UNSUPPORTED_PROOF_REQUIREMENT and prevents template activation.

A new proof family is a protocol upgrade. Before activation it must have a frozen protocol specification, exact implementation and toolchain, negative tests, live local-chain tests, independent human security/privacy review, high-threshold protocol-governance approval, and separate activation. Agents may implement and test it but cannot count toward the human threshold or activate it.

Deprecation blocks new template activations and applies the module's already approved compatibility policy to existing instances. Revocation blocks new proofs prospectively. Neither changes historical receipts, and a new module version never silently migrates an active template.

Stateful authorization transaction

For a template-declared state transition, one successful transaction must:

  1. verify the exact active template and proof module;
  2. verify current authority-root and credential-status-root sequences;
  3. privately verify allocation, issuer eligibility, capability ancestry, session scope, signature, validity, revocation status, exact intent, and selected evidence;
  4. match the public current state commitment and transition sequence;
  5. prove that the template selects exactly one permitted next state;
  6. reject an already-used scoped nullifier;
  7. atomically consume the nullifier, install the next-state commitment, and increment the sequence; and
  8. emit one common receipt.

For a non-transitioning action, the transaction performs the same authorization checks, consumes a nullifier when the action is declared single-use, and emits a receipt without changing state commitment or sequence.

  2. Altering any activation-envelope field, template, module, root sequence, credential status, instance, state commitment, transition sequence, context, action, resource, purpose, recipient, validity, disclosure, signature, or evidence commitment fails.
  3. A stale authority or credential-status root fails even when the private signature was once valid.
  4.   5. A deprecated module cannot be selected by a new template; a revoked module cannot authorize a new proof; existing records remain queryable.
  6. Unsupported module IDs, versions, implementations, configurations, and receipt schemas fail closed without fallback interpretation.
  7. Two transactions built from the same state commitment and sequence cannot both succeed. The winner installs sequence n + 1; the other fails without consuming a second logical transition.
  8. A reused scoped nullifier fails across retries and reconnects.

10 M7 — Gateway and durable receipt transport

Status: NOT_STARTED; depends on M6

Artifacts

  • a long-running observer for the exact allowlisted Midnight network, contract, template registry, proof-module registry, and receipt schema versions;
  • an explicit finality rule and checkpoint cursor persisted before later work is acknowledged;
  • byte-for-byte decoding of the common M6 receipt without private-policy evaluation or module-specific reinterpretation;
  • a durable store containing source event identity, decoded receipt hash, lifecycle state, attempt count, last error category, and next retry time;
  • an outbox uniqueness key derived from Midnight network, contract, transaction, event index, receipt version, and scoped nullifier;
  • an EIP-712 transport signer separated from governance, module approval, allocation, capability issuance, relaying, and registry ownership;
  • versioned verifier-key rotation with overlap and cutoff rules; and
  • restart, reorg, malformed-event, unknown-version, key-rotation, retry, and crash-boundary integration tests.

Processing sequence

  1. Resume from the persisted finalized checkpoint.
  2. Read only finalized events from an allowlisted M6 deployment.
  3. Verify source identity, template and proof-module status at the source sequence, receipt schema, validity window, and exact encoded field lengths.
  4. Insert the source event and receipt into the durable outbox transactionally; a duplicate uniqueness key returns the existing row.
  5. Sign the unchanged typed envelope with the currently active gateway key.
  6. Deliver it to an authorized relayer or recipient endpoint.
  7. Persist acknowledgement or a classified retry state before advancing work.
  8. On a source reorganization before finality, discard the unfinalized event; after the declared finality boundary, an inconsistency stops processing and raises an operator-visible integrity error.

Acceptance

  1. The gateway receives no private credential, record, witness, session key, or plaintext evidence.
  2. It signs only allowlisted receipt and template versions from configured Midnight sources.
  3. Restarting at every durable boundary produces at most one logical execution record.
  4. A stale, reorged, malformed, unknown, or expired source is rejected.
  5. Gateway authority is separate from governance, issuer, allocator, Agent, and relayer authority.
  6. The gateway signs exactly the fields emitted by M6 plus the transport-domain chain and contract binding; it cannot change recipient, purpose, expiry, module, template, commitments, nullifier, or source reference.
  7. A crash before or after every persistence, signing, delivery, and acknowledgement boundary resumes without losing the event or creating a second logical outbox record.
  8. Key rotation identifies which key signed every envelope and rejects keys before activation or after cutoff.

Exit gate

M7 fails if the gateway re-evaluates private policy, silently widens a receipt, or relies on in-memory retry state.

Concrete bridge sequence

  1. The source context selects an explicit record manifest. Every entry contains a record commitment, media/type descriptor, byte length, and ciphertext digest; it never contains the plaintext record in a public artifact.
  2. Before signing, the client displays source and destination contexts, exact recipient encryption-key fingerprint, purpose, selected records, expiry, permitted use, and the new cross-context linkage.

  1. The user sees source context, destination context, recipient, purpose, selected records, expiry, and newly created link before authorization.

  4. Unrelated records and other instances cannot be enumerated.
  5. Changing recipient, purpose, record set, destination context, or case scope invalidates the bridge.

4 M1——现有收据协议基线

实现提交：d5982c9d1994adc63ad6e2c644670cecc59914d5
验收证据：docs/evidence/M1/acceptance.json

通俗结果说明

M1 实现了第一个可执行的公开收据切片。它回答一个范围有限的问题：当上游隐私系统已经产生 授权后，验证者如何签署一份精确、绑定接收方的声明，以及 Monad 兼容合约如何拒绝被修改、 过期、未经授权或重复使用的声明。

M1 不回答上游私有操作是否真实有效。现有 Solidity 合约验证网关／验证者签名和公开收据约束， 但不验证 Midnight 证明。

具体协议数据

@permio/protocol 定义版本化 schema 与用途标识符、带长度前缀的规范 commitment 输入，以及 EIP-712 类型化数据布局。EIP-712 是对具名结构化字段签名的 Ethereum 标准，避免对含义模糊的 字节串签名。

公开背书绑定：

  • schema ID；
  • Midnight 来源网络、合约和交易哈希；
  • 操作 commitment 与限定范围 nullifier；
  • 用途哈希与精确 Monad 接收方；
  • 签发与到期时间；以及
  • EIP-712 链 ID 和验证合约域。

限定范围 nullifier 是限制在特定 schema、用途和接收方内的一次性标识。它防止同一权益被重复 消费，同时不公开用户可重复使用的身份。

已实现交易流程

  1. 获授权验证者对精确 EIP-712 背书签名。
  2. 中继器把背书和签名提交给 RecipientBoundAttestationRegistry.registerAttestation。
  3. 合约检查时间有效性、精确接收方、验证者授权、签名恢复和未使用的重放范围。
  4. 成功时，合约记录背书并消费该范围。
  5. 失败时，不写入背书记录或重放状态。

测试与负向案例

  • 协议测试证明 schema 和用途哈希与已提交向量一致；
  • 规范编码能区分朴素拼接会混淆的输入；
  • commitment 域彼此隔离，防止一种哈希被当作另一种使用；
  • Solidity 与 TypeScript 对 EIP-712 字段顺序和类型哈希达成一致；
  • 有效中继注册可在 Hardhat 本地 EVM 成功；
  • 替换接收方、重复使用和未授权验证者均失败；以及
  • 撤销验证者后，其后续签名不再被接受。

已验证证据与限制

验收使用 Node.js 24.13.1、npm 11.8.0、TypeScript 7.0.2、Hardhat 3.14.0 和 viem 2.55.19。npm run check 通过六个协议测试和六个已部署合约测试。

手写 Alice/Bob/Clara fixture 只保留为 M1 历史测试证据。新情境工作必须使用 M3 生成器。M1 没有实现情境模板、治理、上下文账户、网关或 Midnight 证明验证。

退出门槛

如果 TypeScript 与 Solidity 对同一 payload 得出不同哈希、背书可以被重放或转给另一个接收方， 或者中继器无需获授权验证者签名即可创建授权，则 M1 不算完成。

  1. parseScenarioTemplate 拒绝不是精确 JSON 数据的值。

6 M3——确定性情境生成器

状态：DONE；依赖 M2
实现提交：38227d45c7a2f409ebeb0a0d1be0bec877cdaecc
验收证据：docs/evidence/M3/acceptance.json

通俗结果说明

M3 用可复现的合成测试实例替代手写示例身份和记录。只要经过验证的模板、精确模板哈希、生成器 版本、test: 种子和策略 profile 相同，每次运行都会产生相同的规范字节。改变种子会改变生成 主体与记录，而不需要改变源码或情境 schema。

该生成器只用于测试、演示和验收证据。它不是生产身份生成器，也不会读取生产数据。

产物包括版本化生成器接口、带种子的合成主体/记录/凭证/事件/时间戳、公开/私有分类 manifest、 golden-vector 格式和产物隐私扫描器。

生成流程

  1. 验证 M2 模板并重新计算精确哈希。
  2. 模板与调用方提供的哈希不一致时拒绝。
  3. 验证生成器版本、显式 test: 种子和策略 profile。
  4. 从带长度前缀的输入导出主 SHA-256 digest。
  5. 在各自版本化哈希域下导出主体、记录、凭证、声明、事件和时间戳。
  6. 为每个“上下文 + 参与者 slot”组合导出不同主体，避免复用 slot 形成全局跨上下文标识。
  7. 私有实例数据与 allowlist 构造的公开 schema 摘要分别生成。
  8. 重新构建完整分类 manifest，并在接受任何公开产物前执行扫描。

生成器不读取系统时钟、操作系统随机源、locale、环境变量或机器状态。所有合成值带 syn_ 前缀，使 fixture 能拒绝意外混入的生产数据。

验收必须证明：相同输入产生字节一致向量；不同种子改变实例值但不改变模式或源码；所有数据均为 合成数据；私有字段出现在公开收据、账本 dump、日志或 HTML 时扫描失败。

扫描器还检查原始、JSON 转义、HTML 转义、数字实体、URL 编码、十六进制、Base64 和 Base64URL 形式。分类 manifest 每次都从生成结构重新导出；调用方不能通过删除或放宽私有条目绕过检查。 npm run generate:golden --workspace @permio/scenario-generator 必须逐字节重现已提交向量。

7 M4——模板治理与情境库

状态：DONE；依赖 M2，并已集成在 M3 之后
实现提交：9b76d6117cabf7211b5077c12357bdc6a3cd251e
验收证据：docs/evidence/M4/acceptance.json
开发日志：docs/evidence/M4/development-log.md

通俗结果说明

M4 决定某个精确 M2 模板版本何时可以用于创建新情境实例。它把创建草稿、报告验证风险、审核 精确内容、激活、分配实例、退役和紧急撤销分开。不存在可以完成全部动作的万能管理员。

模板由四个不可分割的值标识：namespace、template ID、语义版本和精确 SHA-256 内容哈希。批准 其中一个组合，不会批准另一个版本或被修改的内容。

产物包括草拟、验证、审核、激活、退役和撤销状态；对精确模板哈希的审核者背书；命名空间阈值 治理；不可变活跃版本注册表；以及作者、审核者、治理方和分配器的权限测试。

packages/scenario-governance 实现生命周期注册表、权限策略、稳定错误代码、Ed25519 审核者 背书、不可变历史记录和十六个治理测试。

权限模型

每个 namespace 策略包含五组互不重叠的主体：

  • 作者创建草稿，并且只能推进自己的草稿完成验证；
  • 审核者使用已登记公钥批准或拒绝精确目标；
  • 治理方在满足审核阈值后激活版本，并可退役活跃版本；
  • 分配器只能为精确、活跃的版本申请一次实例创建权限；以及
  • 紧急撤销者可以前瞻性停止活跃或已退役版本。

策略创建会拒绝出现在多个集合中的同一主体、重复审核者身份、重复审核者密钥、空的必要权限 集合，以及无法达到的阈值。Agent 或作者身份不会隐式授予审核、激活、分配或撤销权限。

生命周期与精确转换

draft -> validated -> in_review -> active -> retired
                                    |          |
                                    +-> revoked<+
  1. createDraft 重新解析 M2 模板、计算精确哈希，并占用 namespace/template/version 谱系。
  2. recordValidation 以 grantsTrust: false 保存结构与风险发现，不能批准或激活任何内容。
  3. submitForReview 冻结供审核者决定的精确目标。
  4. submitReview 验证审核者资格，以及对 namespace、template ID、版本、内容哈希、审核者、 决定和时间的签名。
  5. activate 要求独立治理主体、足够多的唯一批准、没有拒绝记录，并且没有重复审核决定。
  6. authorizeInstantiation 要求分配器、唯一 request ID、精确活跃目标和当前 active 状态。
  7. retire 阻止未来分配，但保留激活和此前分配历史。
  8. revoke 记录带原因的明确前瞻性紧急停止，不改写早期记录。

验收必须证明：作者和 Agent 可草拟但不能自行激活高影响共享模板；验证工具不能授予信任； 激活满足阈值；退役只阻止新实例而不改写历史收据；分配器只能实例化活跃版本。

此外，任何目标字段、审核者身份、决定、时间、密钥、签名域或签名发生变化都必须让审核签名 失效；即使批准数量达到阈值，只要存在拒绝也不能激活；终止时间不能早于已经签发的实例授权； 调用方不能通过修改返回对象篡改注册表历史。

负向测试与已验证证据

十六个测试覆盖未授权作者、权限集合重叠、Agent 提权、同版本替换内容、无效状态转换、验证试图 授予信任、修改哈希和已签字段、不合格及重复审核者、阈值不足、审核拒绝、分配／治理权限坍缩、 激活前分配、退役、撤销、回填时间和修改返回记录。

验收 npm run check 通过六个协议、十五个情境领域、十四个生成器、十六个治理和六个已部署合约 测试。M4 仍是内存中的链下治理包；它不声称 Midnight 已经执行该生命周期。

8 M5——上下文账户与有限会话

状态：DONE；依赖 M2 和 M4
实现提交：c65cfe1dfcc31019754ac807b00819ec55b0542b
验收证据：docs/evidence/M5/acceptance.json
开发日志：docs/evidence/M5/development-log.md

通俗结果说明

M5 把一份 M4 批准的分配转换为运行中的情境实例，并判断某个已签名操作是否可以改变该实例。 它不把“管理员”“商家”或“Agent”等全局角色当作权限。权限始终来自绑定到一个精确模板、实例、 上下文、操作范围、接收方范围、用途、披露策略和时间窗口的 capability。

上下文账户不是登录账户。它是一把绑定到一个情境实例和一个模板定义上下文的公钥。注册只创建 这层绑定，不授予任何操作。实例中明确列出的签发者必须先创建根 capability，账户才能执行动作。

产物包括 ScenarioInstance、ContextAccount、CapabilityGrant、ActionIntent、能力收缩/ 到期/撤销/委托深度、会话密钥，以及人、服务、合约和 Agent 主体类型。

具体实现位于 packages/context-accounts，包含运行时模型、Ed25519 ActionIntent 签名与验证、 授权系统、稳定错误类型和十三个测试。人、服务、合约和 Agent 主体全部使用相同 capability 检查。

实例创建

  1. createScenarioInstance 加载尚未使用的 M4 实例化授权。
  2. 重新加载受治理模板，并要求创建实例时模板仍为 active。
  3. 重新解析 M2 模板并计算哈希，将 namespace、template ID、版本和哈希与 M4 授权逐项比较。
  4. 记录分配器、模板初始状态、实例期限和显式 capability 签发者。
  5. M4 分配只能消费一次。旧分配不能复用；退役前签发的分配不能在退役后创建实例。

Capability 与会话规则

Capability 列出允许的操作、资源 selector 与具体资源、用途、接收方类型与精确接收方、披露策略、 有效窗口和剩余委托深度。子 capability 必须是父 capability 的严格子集：至少缩小一个维度， 不能增加任何值，不能更早开始或更晚结束，也不能增加委托深度。实现把深度上限设为 16，并把 任一祖先 capability 的撤销传播给所有后代。

会话使用全新的 Ed25519 公钥和一个 capability 的严格子集。账户密钥不能复用为会话密钥，同一 密钥也不能跨上下文账户复用。这些规则防止便利的复用密钥意外成为公开的跨上下文标识符。

已签操作与授权流程

已签 ActionIntent 绑定精确模板目标、实例、会话、上下文、操作、资源 selector、具体资源、 用途、接收方类型、精确接收方、披露策略、签发时间和会话范围 nonce。

authorizeAction 按以下顺序检查：

  1. 会话存在且 Ed25519 签名有效；
  2. 模板、实例和上下文精确匹配；

弃用阻止新模板激活，并对现有实例执行此前已经批准的兼容策略。撤销前瞻性阻止新证明。两者 都不改变历史收据；新模块版本绝不能静默迁移活跃模板。

每个执行 adapter 针对一个精确收据 schema 版本和 action schema 登记。调用接口只接收公开 收据与 adapter 特定公开执行参数；它不能读取私有证据，也不能把 outputCommitment 重新解释 为额外权限。

网关签名者不能仅凭签名为自己授权、改变注册表所有权或登记新 adapter。注册表治理、网关签名 密钥轮换、adapter 登记、紧急暂停／撤销、中继和接收方消费必须是不同权限。Hardhat 本地节点 测试必须部署泛化注册表与 adapter，通过独立中继器提交 M7 fixture，检查事件与存储，并对已部署 合约执行全部拒绝路径。下游执行失败按照 adapter 合约记录或返回，但不改写成功的 Midnight 授权收据。
