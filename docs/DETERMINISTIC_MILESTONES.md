# Permio Deterministic Milestones

Status: revised execution contract<br>
Date: 10 October 2026<br>
Scope: programmable scenario library, context-bound accounts, generated scenario packs, Midnight authorization, and composable execution

## 1 How completion is judged

“Deterministic” means every milestone has named artifacts, executable checks,
privacy invariants, negative cases, and a binary exit gate. It does not mean
that participant names or scenario data are fixed in architecture.

All concrete examples are generated by:

```text
templateHash + generatorVersion + explicitSeed + policyProfile
  -> synthetic scenario instance and expected test vectors
```

The seed is recorded for reproducibility. Generated values are disposable and
must never become protocol constants, source-code branches, contract literals,
or hand-written architecture requirements.

### 1.1 Architecture status versus implementation status

The programmable scenario library, context accounts, scoped capabilities,
three required scenario profiles, and separation of privacy authorization from
execution are binding Permio design decisions, not optional future ideas. A
milestone marked `NOT_STARTED` means the current checkout has not yet
implemented that part of the authoritative design; it does not authorize an
alternative fixed-domain architecture. Existing code is either conforming,
partially conforming, or pending migration.

## 2 Global gates

Every milestone must preserve these rules:

1. No global public pseudonym links a principal across scenario instances or
   contexts.
2. An authorization binds template version, instance, context, action,
   resource, purpose, recipient, time, and disclosure policy.
3. Delegation attenuates authority and has a bounded depth.
4. Agents never receive blanket access or template self-approval power.
5. Private records and witnesses never enter the gateway, execution chain,
   public application store, logs, or generated documentation.
6. Privacy decisions and high-throughput execution use a versioned receipt
   boundary.
7. Cross-context bridges are explicit, recipient-bound, purpose-bound,
   selected-record-bound, expiring, and tested against replay.
8. A proof establishes only encoded claims, never the truth of an opinion,
   allegation, diagnosis, prediction, or human judgment.
9. Tests use generated synthetic instances; production inputs never reuse test
   seeds.

## 3 M0 — Documentation and naming baseline

Status: `DONE`

### Artifacts

- human-first guide;
- programmable context architecture;
- deterministic milestone contract;
- bilingual generated HTML; and
- documentation generator with Mermaid support.

### Acceptance

3. Documentation build and freshness checks pass.
4. English and Chinese panels contain the same sections.

### Exit gate

M0 fails if a canonical architecture section contains literal participant,
record, credential, case, product, amount, or timestamp fixtures.

## 4 M1 — Existing receipt-protocol baseline

Status: `DONE`; historical evidence remains in `docs/evidence/M1`

The repository already contains a canonical receipt schema package, EIP-712
encoding, hash vectors, a recipient-bound Solidity registry, and integration
tests. Its named hand-written scenario fixture is retained only as historical
evidence for that completed baseline. New architecture and tests must migrate
to the generator introduced in M3; the legacy fixture is not a template,
protocol requirement, or source for new acceptance criteria.

M1 remains complete only as a record of the implemented receipt slice. It does
not claim that scenario templates, context accounts, or generic Midnight
authorization are implemented.

## 5 M2 — Scenario-template domain package

Status: `DONE`; depends on M0; acceptance evidence is recorded in
`docs/evidence/M2/acceptance.json`

### Artifacts

- `ScenarioTemplate`, `ContextDefinition`, `ActionDefinition`, and transition
  schemas;
- canonical serialization and versioned template hash;
- template namespace and semantic-version rules;
- validator error taxonomy; and
- unit and property tests.

### Acceptance

1. Unknown fields, missing fields, invalid references, unreachable states, and
   duplicate identifiers fail validation.
2. Canonicalization is stable across object-key order and supported runtimes.
3. An incompatible schema change requires a new template or protocol version.
4. The domain package imports no application-specific scenario module.

### Exit gate

M2 fails if supported contexts or actions are a closed TypeScript union tied to
one use case, or if validation executes arbitrary template code.

### Implemented result

`packages/scenario-domain` now owns the open template model, exact schema
validation, graph and cross-reference checks, canonical Unicode-normalized
serialization, length-delimited domain-separated SHA-256 hashing, and template
revision compatibility. Its tests permute object-key order, exercise invalid
graphs and references, prove that accessor code is not executed, and enforce a
local-only production import boundary. Scenario catalog entries remain data to
be governed in M4 and instantiated by the M3 generator; none is embedded as a
closed application type.

## 6 M3 — Deterministic scenario generator

Status: `NOT_STARTED`; depends on M2

### Artifacts

- versioned generator interface;
- seeded synthetic principal, record, credential, event, and timestamp
  generation;
- public/private classification manifest;
- golden-vector format; and
- artifact privacy scanner.

### Acceptance

1. The same template hash, generator version, seed, and policy profile produce
   byte-identical canonical vectors.
2. A different seed changes instance values without changing schemas or source
   code.
3. Generated fixtures contain synthetic data only.
4. The scanner fails when a field classified private appears in a public
   receipt, ledger dump, log, or generated HTML.

### Exit gate

M3 fails if new tests import a hand-written named scenario fixture or compare
against instance literals stored in architecture documents.

## 7 M4 — Template governance and library

Status: `NOT_STARTED`; depends on M2

### Artifacts

- draft, validation, review, activation, retirement, and revocation states;
- reviewer attestations over exact template hashes;
- namespace governance and threshold-approval model;
- immutable active-version registry; and
- authorization tests for authors, reviewers, governance, and allocators.

### Acceptance

1. Authors and Agents may draft but cannot self-activate a high-impact shared
   template.
2. Validation tools report risk but cannot grant trust.
3. Activation requires the configured threshold for the namespace.
4. Retiring a template prevents new instances without rewriting historical
   receipts.
5. An allocator can instantiate only an active version.

### Exit gate

M4 fails if one administrator role implicitly owns authoring, approval,
allocation, upgrades, and emergency revocation.

## 8 M5 — Context accounts and scoped sessions

Status: `NOT_STARTED`; depends on M2 and M4

### Artifacts

- `ScenarioInstance`, `ContextAccount`, `CapabilityGrant`, and `ActionIntent`;
- capability attenuation, expiry, revocation, and delegation-depth logic;
- session-key issuance and verification;
- human, service, contract, and Agent principal types; and
- denial-reason tests.

### Acceptance

1. Registration grants no permanent business role.
2. Every action checks template, instance, context, action, resource, purpose,
   recipient, time, disclosure policy, and revocation state.
3. A child grant cannot exceed any dimension of its parent.
4. A session key can exercise only its declared subset before expiry.
5. Changing one constrained dimension causes a precise denial.
6. An Agent cannot activate templates or create unbounded delegations unless a
   distinct governance capability explicitly permits it.

### Exit gate

M5 fails if login state alone authorizes a domain action or if the database
stores a global role as the source of runtime permission.

## 9 M6 — Generic Midnight authorization boundary

Status: `NOT_STARTED`; depends on M2, M3, and M5

### Artifacts

- approved template and policy hash registry;
- generic capability and `ActionIntent` verification adapters;
- action-specific proof modules selected through versioned schema identifiers;
- scoped-nullifier derivation; and
- public `DecisionReceipt` fields.

### Acceptance

1. Private evidence and witness values remain inside the caller-controlled
   proof boundary.
2. Public output contains only the receipt version, template/version reference,
   instance commitment, context, action schema, purpose, recipient, validity
   window, scoped nullifier, output commitment, and source reference.
3. Nullifier domains separate templates, contexts, actions, resources, and
   policy versions.
4. Replacing recipient, purpose, action, template version, or instance causes
   verification failure or a distinct non-reusable receipt.
5. Unsupported schema identifiers fail closed.

### Exit gate

M6 fails if the Compact contract or adapter branches on generated participant
names, generated identifiers, or one template family's literal values.

## 10 M7 — Gateway and durable receipt transport

Status: `NOT_STARTED`; depends on M6

### Artifacts

- finalized Midnight event observer;
- source-network, contract, transaction, and policy verification;
- versioned typed receipt envelope;
- durable outbox with idempotent retries; and
- gateway key-rotation tests.

### Acceptance

1. The gateway receives no private credential, record, witness, session key, or
   plaintext evidence.
2. It signs only allowlisted receipt and template versions from configured
   Midnight sources.
3. Restarting at every durable boundary produces at most one logical execution
   record.
4. A stale, reorged, malformed, unknown, or expired source is rejected.
5. Gateway authority is separate from governance, issuer, allocator, Agent,
   and relayer authority.

### Exit gate

M7 fails if the gateway re-evaluates private policy, silently widens a receipt,
or relies on in-memory retry state.

## 11 M8 — Execution registry and adapters

Status: `IN_PROGRESS`; the existing recipient-bound registry is a partial
implementation and must be generalized after M6 and M7.

### Artifacts

- versioned `DecisionReceipt` verification;
- signer rotation and threshold-ready governance boundary;
- recipient, purpose, expiry, schema, and replay checks;
- adapter interface for Monad contracts and ordinary applications; and
- negative tests for widening and replay.

### Acceptance

1. The executor performs only the action named by the receipt schema.
2. Wrong recipient, purpose, version, signer, source, expiry, or replay scope is
   rejected.
3. The relayer pays execution cost but cannot create or modify authorization.
4. Execution may fail because local state changed, but failure does not mutate
   the underlying privacy authorization.
5. No stable subject identifier is required by the registry.

### Exit gate

M8 fails if an execution adapter can reinterpret one receipt as a broader
action or if the registry owner also acts as the receipt signer by default.

## 12 M9 — Cross-domain generated scenario packs

Status: `NOT_STARTED`; depends on M3 through M8

### Required packs

1. Clinical referral and research consent.
2. Professional qualification and temporary site access.
3. Delegated financial or purchasing Agent.

Each pack contains a template, policy profile, generator rules, generated
positive and negative instances, disclosure previews, expected receipts, and
privacy scans. It contains no hand-authored participant or record fixture.

### Acceptance

1. The healthcare pack separates treatment, research, and optional emergency
   purposes, recipients, periods, and audit duties.
2. The professional pack proves a current qualification without disclosing a
   full transcript or unrelated history and creates only short-lived access.
3. The Agent pack binds counterparty, action, bounded resource or amount policy,
   expiry, delegation depth, and revocation.
4. All packs run through the same scenario, capability, receipt, gateway, and
   execution interfaces.
5. No pack requires adding a participant name, context literal, or branching
   rule to the core domain.

### Exit gate

M9 fails if “supporting” a new pack means copying the core system and renaming
fields, or if any pack bypasses the common privacy invariants.

## 13 M10 — Encrypted evidence and cross-context bridge

Status: `NOT_STARTED`; depends on M6 and M9

### Artifacts

- selected-record manifest;
- recipient encryption and key-rotation interface;
- explicit cross-context `ActionIntent`;
- bridge receipt and revocation/expiry behavior; and
- evidence-vault verification API.

### Acceptance

1. The user sees source context, destination context, recipient, purpose,
   selected records, expiry, and newly created link before authorization.
2. Ciphertext travels separately from the public receipt.
3. The recipient verifies manifest hashes, source commitments, receipt scope,
   and expiry before decryption.
4. Unrelated records and other instances cannot be enumerated.
5. Changing recipient, purpose, record set, destination context, or case scope
   invalidates the bridge.

### Exit gate

M10 fails if a bridge is implicit, globally reusable, plaintext on a public
ledger, or described as proving the truth of the underlying human claim.

## 14 M11 — Scenario-library product workflow

Status: `NOT_STARTED`; depends on M4, M5, and M9

### Artifacts

- template catalogue and version view;
- draft, review, activation, retirement, and instantiation workflows;

- disclosure and execution preview;
- Agent-session management and revocation; and

### Acceptance

1. The UI never presents account registration as permanent role selection.
2. Users can distinguish template, instance, context, account, capability,

3. Every sensitive action shows recipient, purpose, expiry, disclosed claims,

4. Reviewers see the exact template hash and version being approved.
5. Agents show their active scope and provide immediate revocation.
6. Browser journeys are created from generated packs rather than fixed user

### Exit gate

M11 fails if product navigation assumes one domain, if a perspective selector
impersonates other users, or if administrator credentials appear in the UI.

## 15 M12 — Local and public-network evidence

Status: `NOT_STARTED`; depends on M7 through M11

### Artifacts

- local Midnight and local EVM end-to-end evidence;
- configured public test-network deployment evidence;
- restart, reorg, expiry, revocation, and replay drills;
- redacted receipts and explorer references;
- generated-fixture provenance; and
- final privacy-artifact scan.

### Acceptance

1. At least one generated instance from each required scenario pack completes

2. Public evidence contains template and receipt versions but no private source
   record or stable cross-context subject identifier.
3. Restarting gateway and relayer processes produces no duplicate logical

4. Key holders and authority boundaries match the architecture.
5. Documentation, code, deployments, and recorded evidence describe the same

### Exit gate

M12 fails if either chain is mocked in public-network evidence, if private

success.

For every coherent implementation batch:

```bash
npm test
npm run compile
```

Run the complete repository check when the environment supports it. Record any
toolchain limitation separately; never weaken a privacy or acceptance gate to
hide an environmental failure.

# Permio 确定性里程碑

状态：修订后的执行契约<br>
日期：2026 年 10 月 10 日<br>
范围：可编程情境库、上下文账户、生成式情境包、Midnight 授权与可组合执行

## 1 如何判断完成

“确定性”表示每个里程碑都有具名产物、可执行检查、隐私不变量、负向案例和二元退出门槛。
它不表示参与者姓名或情境数据要写死在架构中。

所有具体示例都由下式生成：

```text
模板哈希 + 生成器版本 + 显式种子 + 策略 profile
  -> 合成情境实例与预期测试向量
```

种子被记录以便复现。生成值是可丢弃数据，绝不能变成协议常量、源码分支、合约字面量或手写
架构要求。

### 1.1 架构状态与实施状态

可编程情境库、上下文账户、有限能力、三个必需情境 profile，以及隐私授权与执行分离，都是
具有约束力的 Permio 设计决策，而不是可选的未来设想。里程碑标记为 `NOT_STARTED`，只表示当前
checkout 尚未实现权威设计的这一部分；它不允许继续采用另一套固定领域架构。现有代码只能是
已经符合、部分符合或等待迁移。

## 2 全局门槛

每个里程碑都必须保持以下规则：

1. 不存在把主体跨情境实例或上下文关联起来的全局公开假名。
2. 授权绑定模板版本、实例、上下文、操作、资源、用途、接收方、时间和披露策略。
3. 委托只能收缩权限，并且深度有界。
4. Agent 永远不会获得全面访问或自行批准模板的权力。
5. 私有记录和见证绝不进入网关、执行链、公开应用存储、日志或生成文档。
6. 隐私决定与高吞吐执行使用版本化收据边界。
7. 跨上下文桥接必须显式、接收方绑定、用途绑定、选定记录绑定、会到期并经过重放测试。
8. 证明只建立已编码声明，绝不证明观点、指控、诊断、预测或人的判断为真。
9. 测试使用生成的合成实例；生产输入绝不复用测试种子。

## 3 M0——文档与命名基线

状态：`DONE`

### 产物

- 面向人的指南；
- 可编程情境架构；
- 确定性里程碑契约；
- 双语生成 HTML；以及
- 支持 Mermaid 的文档生成器。

### 验收

1. 架构拓扑分别呈现控制、隐私、收据、执行和加密证据概念，不再使用一张包揽所有组件的图。
2. 三份源文档都说明具体情境由生成器产生，而不是嵌入代码。
3. 文档构建与新鲜度检查通过。
4. 英文与中文面板包含相同章节。

### 退出门槛

如果规范架构章节包含写死的参与者、记录、凭证、案件、产品、金额或时间戳测试数据，M0 失败。

## 4 M1——现有收据协议基线

状态：`DONE`；历史证据保留在 `docs/evidence/M1`

仓库已经包含规范收据模式包、EIP-712 编码、哈希向量、接收方绑定 Solidity 注册表和集成测试。
其中具名的手写情境数据只作为该已完成基线的历史证据保留。新的架构和测试必须迁移到 M3
引入的生成器；旧数据不是模板、协议要求或新验收条件的来源。

M1 的完成状态只记录已经实现的收据切片，不表示情境模板、上下文账户或通用 Midnight 授权
已经实现。

## 5 M2——情境模板领域包

状态：`DONE`；依赖 M0；验收证据记录于 `docs/evidence/M2/acceptance.json`

产物包括 `ScenarioTemplate`、`ContextDefinition`、`ActionDefinition`、转换模式、规范序列化、
版本化模板哈希、命名空间与语义版本规则、验证错误分类，以及单元和属性测试。

验收必须证明：未知、缺失或重复字段以及无效引用和不可达状态会失败；规范化不受对象键顺序
影响；不兼容变更需要新版本；领域包不导入特定应用情境模块。

如果支持的上下文或操作仍是绑定单一用例的封闭 TypeScript union，或者验证器执行任意模板代码，
M2 失败。

### 已实现结果

`packages/scenario-domain` 现在负责开放式模板模型、精确模式验证、图与交叉引用检查、Unicode
规范化的规范序列化、带长度前缀和域分离的 SHA-256 哈希，以及模板修订兼容性。测试会置换对象键
顺序、覆盖无效图与引用、证明不会执行访问器代码，并强制生产代码只能进行包内导入。情境库条目
仍是将在 M4 中治理、由 M3 生成器实例化的数据；它们没有作为封闭的应用类型嵌入源码。

## 6 M3——确定性情境生成器

状态：`NOT_STARTED`；依赖 M2

产物包括版本化生成器接口、带种子的合成主体/记录/凭证/事件/时间戳、公开/私有分类 manifest、
golden-vector 格式和产物隐私扫描器。

验收必须证明：相同输入产生字节一致向量；不同种子改变实例值但不改变模式或源码；所有数据均为
合成数据；私有字段出现在公开收据、账本 dump、日志或 HTML 时扫描失败。

如果新测试导入手写具名情境数据，或把架构文档中的实例字面量作为断言对象，M3 失败。

## 7 M4——模板治理与情境库

状态：`NOT_STARTED`；依赖 M2

产物包括草拟、验证、审核、激活、退役和撤销状态；对精确模板哈希的审核者背书；命名空间阈值
治理；不可变活跃版本注册表；以及作者、审核者、治理方和分配器的权限测试。

验收必须证明：作者和 Agent 可草拟但不能自行激活高影响共享模板；验证工具不能授予信任；
激活满足阈值；退役只阻止新实例而不改写历史收据；分配器只能实例化活跃版本。

如果一个管理员角色隐式拥有编写、批准、分配、升级和紧急撤销全部权力，M4 失败。

## 8 M5——上下文账户与有限会话

状态：`NOT_STARTED`；依赖 M2 和 M4

产物包括 `ScenarioInstance`、`ContextAccount`、`CapabilityGrant`、`ActionIntent`、能力收缩/
到期/撤销/委托深度、会话密钥，以及人、服务、合约和 Agent 主体类型。

验收必须证明：注册不授予永久业务角色；每次操作检查全部约束维度；子授权不超过父授权；会话
密钥只能在到期前行使声明子集；改变任一约束维度会得到精确拒绝；Agent 不会隐式获得治理权。

如果登录状态本身可以授权领域操作，或数据库把全局角色作为运行时权限来源，M5 失败。

## 9 M6——通用 Midnight 授权边界

状态：`NOT_STARTED`；依赖 M2、M3 和 M5

产物包括批准的模板/策略哈希注册表、通用能力与 `ActionIntent` 适配器、通过版本化模式标识符
选择的操作证明模块、限定范围空值标识，以及公开 `DecisionReceipt` 字段。

验收必须证明：私有证据留在调用者控制的证明边界；公开输出只有最小版本化收据；空值标识域
分离模板、上下文、操作、资源和策略版本；替换任何绑定维度都会失败或产生不可复用的新收据；

如果 Compact 合约或适配器根据生成的姓名、标识符或某一模板族的字面值分支，M6 失败。

## 10 M7——网关与持久化收据传输

状态：`NOT_STARTED`；依赖 M6

产物包括 Midnight 最终确认观察器、来源验证、版本化类型收据封装、持久化 outbox 和密钥轮换
测试。

验收必须证明：网关不接收私有数据；只为允许的来源和版本签名；在每个持久化边界重启仍最多
产生一个逻辑执行记录；陈旧、重组、畸形、未知或过期来源被拒绝；网关权限与其他权限分离。

如果网关重新评估私有策略、扩大收据或依赖内存重试状态，M7 失败。

## 11 M8——执行注册表与适配器

状态：`IN_PROGRESS`；现有接收方绑定注册表只是部分实现，必须在 M6 和 M7 后泛化。

产物包括版本化收据验证、签名者轮换、接收方/用途/期限/模式/重放检查、Monad 与普通应用适配器，

验收必须证明：执行器只执行收据具名操作；错误维度被拒绝；中继器只能付费而不能创建授权；

如果适配器能把一份收据解释为更宽操作，或注册表所有者默认同时担任收据签名者，M8 失败。

## 12 M9——跨领域生成式情境包

状态：`NOT_STARTED`；依赖 M3 至 M8

必需情境包为：临床转诊与研究同意、专业资格与临时场地访问、受委托金融或采购 Agent。

每个包包含模板、策略 profile、生成规则、生成的正负实例、披露预览、预期收据和隐私扫描，
不包含手写参与者或记录测试数据。

验收必须证明三个包各自覆盖其核心隐私转换，并通过同一情境、能力、收据、网关和执行接口；
添加新包不需要在核心领域添加参与者姓名、上下文字面量或分支规则。

如果支持新包等同于复制核心系统再改字段名，或某个包绕过公共隐私不变量，M9 失败。

## 13 M10——加密证据与跨上下文桥接

状态：`NOT_STARTED`；依赖 M6 和 M9

产物包括选定记录 manifest、接收方加密与密钥轮换接口、显式跨上下文 `ActionIntent`、桥接收据
与撤销/到期行为，以及证据保险库验证 API。

验收必须证明：授权前展示来源/目标上下文、接收方、用途、记录、期限和新增关联；密文与公开收据
分开；接收方在解密前验证所有绑定；无关记录不可枚举；改变任何桥接维度都会失败。

如果桥接是隐式、全局复用、公开明文，或被描述为证明人类声明为真，M10 失败。

## 14 M11——情境库产品工作流

状态：`NOT_STARTED`；依赖 M4、M5 和 M9

产物包括模板目录与版本视图、治理工作流、槽位分配、能力委托、披露与执行预览、Agent 会话撤销，
以及由生成情境包创建的多账户浏览器旅程。

验收必须证明：注册不要求永久角色；用户能区分模板、实例、上下文、账户、能力、会话、证明、
收据、执行和证据交付；敏感操作在确认前展示所有关键绑定；审核者看到精确哈希与版本；Agent
范围可见且可立即撤销；生产 UI 不包含固定情境运行器。

如果产品导航假定一个领域、透视选择器可以冒充用户，或管理员凭据出现在界面中，M11 失败。

## 15 M12——本地与公共网络证据

状态：`NOT_STARTED`；依赖 M7 至 M11

产物包括本地双链证据、公开测试网络部署证据、重启/重组/到期/撤销/重放演练、脱敏收据、
浏览器引用、生成数据来源记录和最终隐私扫描。

验收必须证明：每个必需情境包至少一个生成实例走完授权到执行；公开证据无私有记录和跨上下文
稳定标识符；重启不产生重复逻辑操作；密钥持有人符合架构；文档、代码、部署和证据描述同一版本。

如果公开网络证据模拟任一链、私有测试数据公开，或失败交易被展示为成功，M12 失败。

## 16 必需验证顺序

每个完整实施批次运行：

```bash
npm run docs:check
npm run typecheck
npm test
npm run compile
```

环境支持时运行完整仓库检查。工具链限制应单独记录，绝不能通过削弱隐私或验收门槛隐藏环境失败。
