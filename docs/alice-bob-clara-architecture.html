Composite architecture · 9 October 2026

A private fact proved once and consumed only where intended

Concrete architecture for Alice the merchant, Bob the purchaser, and Clara the regulator across Midnight and Monad. The design defines every private input, public output, commitment, nullifier, recipient view, bridge step, key, and finality boundary.

Midnight Compact Monad EVM EIP-712 Recipient-bound No global identity

1. Architecture decision

Permio uses two chains because they solve different problems. Midnight proves narrowly scoped facts about private records. Monad makes those approved results easy for an EVM application to consume. A purpose-built gateway is the explicit MVP trust boundary.

Midnight

Verifies credential provenance and control, rating range, support-window policy, scoped uniqueness, selected-record integrity, and recipient-bound bridge authorization.

Permio gateway

Reads finalized public Midnight results only, applies a versioned schema policy, derives a Monad-specific nullifier, and signs an EIP-712 attestation.

Monad

Verifies the gateway signature, recipient, purpose, expiry, and replay scope, then exposes a standard EVM receipt to one intended application or recipient.

Trust statement. The first version is not a trustless cross-chain light client. Monad trusts an authorized gateway verifier to have checked the correct Midnight network, contract, transaction, and public state.

4. Complete information flows

4.1 Credential issuance

  1. A contract authority registers Alice's dedicated Jubjub issuer public key as Midnight issuer 1.
  2. Bob's client generates a random holder secret s_B and sends Alice only its holder binding.
  3. Alice signs the private purchase credential containing merchant, product, purchase day, order, credential, and holder binding.
  4. Bob stores the credential and s_B in encrypted account-scoped Midnight private state. No per-purchase chain transaction is required.

4.2 Reputation

  1. Bob authors exactly two fields: rating and free-form review text.
  2. The UI previews the public view, hidden credential fields, recipient, purpose, and new linkage.
  3. publishReview verifies Alice's signature, Bob's holder binding, rating range, and unused review scope.
  4. Midnight discloses only a review-scoped nullifier and review commitment.
  5. The public review store publishes Bob-approved content. An optional Monad receipt certifies eligibility and uniqueness, never opinion truth.

4.3 Customer support

  1. Bob previews Alice as recipient and four predicates: Alice-issued credential, H1 product, age at most 30 days, and unused entitlement.
  2. openSupportCase verifies the credential, date range, and a support-specific nullifier distinct from the review nullifier.
  3. The gateway observes the confirmed public result and signs PERMIO_SUPPORT_ELIGIBLE_V1 for Alice's support address or contract.
  4. A neutral relayer registers it on Monad. Alice calls isValidFor before advancing the case.
  5. Alice signs a structured support decision. The target V2 circuit verifies her signature without requiring Bob's holder secret again.

4.4 Regulatory escalation

  1. Bob selects the exact review snapshot, support case, and Alice decision.
  2. The preview names Clara, the case, purpose, records, policy version, expiry, and every newly disclosed link.
  3. Bob explicitly authorizes authorizeRegulatoryBridgeV2.
  4. The circuit privately proves that the selected records derive from the same credential and publishes one Clara-, case-, purpose-, evidence-, and policy-bound bridge.
  5. Bob separately encrypts the selected plaintext evidence to Clara's case key. The ZK bridge proves linkage; it does not transport the evidence.
  6. The gateway issues PERMIO_REGULATORY_BRIDGE_V1 on Monad. Alice gains no review-to-Bob link as a side effect.

5. Zero knowledge circuit design

All protocol hashes use explicit, versioned domain separation. Any incompatible encoding change creates a new domain version.

holderBinding = H("permio:holder:v1", s_B)

N_review = H("permio:review-nullifier:v1",
             s_B, credentialId, merchantId, productId)

N_support = H("permio:support-nullifier:v1",
              s_B, credentialId, merchantId, productId)

C_review = H("permio:review-record:v1",
             merchantId, productId, N_review,
             rating, H(reviewText), publishedAt)

C_support = H("permio:support-record:v1",
              merchantId, productId, N_support,
              caseId, remedy, policyVersion, openedAt)

C_decision = H("permio:support-decision:v2",
               N_support, C_support, outcome,
               reasonCommitment, decidedAt, policyVersion)

evidenceSetHash = H(C_review, C_support, C_decision)

K_bridge = H("permio:regulatory-bridge-key:v2",
             Clara, regulatorCase, purpose,
             evidenceSetHash, policyVersion)

C_bridge = H("permio:regulatory-bridge-record:v2",
             K_bridge, s_B, evidenceSetHash,
             authorizedAt, policyVersion)

N_review and N_support are intentionally different. The private holder secret inside C_bridge prevents a public observer from recomputing the cross-context linkage from public records.

6. Monad attestation design

The existing RecipientBoundAttestationRegistry is shared by all schemas. EIP-712 binds every signature to the exact data shape, Monad chain ID, and registry address.

Monad-specific relay nullifier

N_monad = H("permio:monad-relay:v1",
            midnightScopedNullifier,
            schemaId, purposeHash, recipient,
            monadChainId, registryAddress)

Monad does not copy the raw Midnight nullifier. The derived value cannot be replayed on another EVM chain or registry. A Midnight transaction hash remains an intentional provenance link between one source action and one receipt; hashing public data is not secrecy.

7. Gateway validation and lifecycle

  1. Match the configured Midnight network and exact Compact contract.
  2. Fetch the transaction and public contract state from the indexer.
  3. Require the expected action and configured confirmation threshold.
  4. Check that the public nullifier or bridge key maps to the expected commitment.
  5. Apply the versioned schema policy and recipient allow-list.
  6. Derive N_monad, sign EIP-712, and persist an idempotent outbox row.
  7. Submit through a separate relayer, wait for Monad finality, and save the receipt.
Draft→ Policy approved→ Proving→ Midnight submitted→ Midnight confirmed→ Attestation signed→ Monad submitted→ Monad finalized→ Consumed or revoked

The outbox idempotency key binds the Midnight network, contract, transaction, schema, purpose, recipient, Monad registry, and chain ID. No witness input is serialized into a gateway job, log, trace, error report, or Monad transaction.

Key separation

The Midnight contract authority, Alice issuer, Bob holder secret, Bob Midnight wallet, gateway verifier, Monad relayer, Monad registry owner, and Clara case decryption key are distinct authorities. No key is reused across those roles.

10. Implementation plan

  1. Freeze protocols. Version the three schema IDs, purpose vocabulary, canonical encodings, relay nullifier, and V2 circuit domains in tests.
  2. Fix the privacy boundary. Implement recordSupportDecisionV2 so Alice never needs Bob's secret.
  3. Port Midnight modules. Move selected Compact sources, adapters, transaction service, and three-actor fixtures into Permio.
  4. Build support first. Implement the public-output observer, schema policy, signer, persistent outbox, and Monad publisher for support only.
  5. Prove locally. Run Midnight Local Dev to Hardhat end-to-end, including replay, substitution, restart, and failure recovery.
  6. Deploy publicly. Publish the registry to Monad Testnet and the Compact contract to Midnight Preprod; record versions and addresses.
  7. Complete all contexts. Add review and regulatory schemas through the same registry and gateway.
  8. Integrate the product. Port the account-first UI, explicit disclosure previews, and two-chain lifecycle receipts.

中文架构摘要

Permio 使用 Midnight 证明私有事实，使用 Monad 向指定应用或接收方提供可组合的公开收据。网关是 MVP 阶段明示的信任边界，只能读取已经确认的 Midnight 公开输出，不能获得 Bob 的凭证、持有人秘密或明文证据。

角色

Alice 是商家、购买凭证签发者和客服决定者；Bob 是购买者、评价者、客服申请者和跨上下文桥接授权者；Clara 是监管接收方。这些名字只是场景标签，系统不创建全局公开身份。

信息流

Bob 生成持有人秘密，Alice 只签署其绑定值所在的私有购买凭证。Bob 在 Midnight 上分别生成评价和客服证明，两者使用不同的域分离空值标识。Alice 的客服决定由 Alice 独立签名，V2 电路不得再次要求 Bob 的秘密。监管升级时，Bob 明确选择评价、客服和决定，授权一个只对 Clara、指定案件、用途、证据集合和策略版本有效的桥接，并单独把明文证据加密给 Clara。

两条链

Midnight 账本只公开签发者公钥、限定范围空值标识和动作承诺。网关核对 Midnight 网络、合约、交易和公开状态后，签署 EIP-712 证明。Monad 注册表检查验证者、接收方、用途、有效期和重复使用，并向 Alice 的客服应用或 Clara 的案件提供标准 EVM 收据。Bob 不需要 Monad 地址或交易。

第一实施切片

先完成客服资格：Bob 在 Midnight 上证明购买不超过 30 天且权益未使用；网关签发短期的 PERMIO_SUPPORT_ELIGIBLE_V1；中立中继器在 Monad 上注册；Alice 的客服系统用 isValidFor 验证。随后再通过同一注册表增加评价和监管模式。
